# Discovery phase proposal template

Internal note: Replace bracketed text, remove guidance lines, and keep the selected package language aligned with the package documents before sending this proposal to a client. Build the proposal from the package summary documents and use `../Packages/internal_package_operating_model.md` plus the relevant facilitator guide to plan the actual delivery sequence. Do not mention internal AI or workflow mechanics in the client proposal.

## Proposal summary

* **Client:** [Client name]
* **Prepared by:** [Name]
* **Date:** [Date]
* **Recommended package:** [Package A / Package B / Package C]
* **Timeline:** [5 business days / 2 weeks / up to 4 weeks]
* **Investment:** [Amount or pricing model]
* **Primary decision this phase will support:** [Short sentence]

## 1. Why this work now

Use one short paragraph.

Describe the business trigger, the risk of moving into delivery too early, and why the client needs clarity now.

Suggested structure:

`[Client name]` is currently facing `[business issue or opportunity]`. The main risk is that delivery starts before there is enough clarity on `[problem, journey, or service implications]`. This discovery phase is designed to give `[decision-makers]` a stronger basis for `[investment decision, scope decision, prioritization decision, or change decision]`.

## 2. Decision this phase will support

State the decision in direct terms.

Examples:

* Should we invest in improving this journey now, later, or not at all?
* Which concept direction should move into delivery?
* What should be built first, and what should be deferred?
* What service changes are required for the concept to work in practice?

## 3. Scope

List the focus of the work:

* **Users or customer groups:** [Who is in scope]
* **Journey, product, or service area:** [What is in scope]
* **Channels or touchpoints:** [Where the experience happens]
* **Internal teams or systems:** [Who or what influences the experience]

Also state what is out of scope:

* [Out-of-scope item]
* [Out-of-scope item]

## 4. Recommended package

Use one short paragraph to explain why this package fits the problem.

Suggested structure:

We recommend **[Package name]** because `[reason based on scope, complexity, and decision type]`. The client already knows `[known factors]`, but still needs clarity on `[unknown factors]` before delivery scope and investment can be set with confidence.

## 5. Core activities

Use the exact activity language from the selected package in `../Packages/strategic_ux_packages.md` and the matching detailed package file.

Format this section as a short list of concrete activities, including:

* Method or format
* Duration
* Participant type
* Purpose
* Input the client must provide before the activity starts
* Output the client will review and validate before the next activity begins
* How the activity feeds the next step

Example structure:

* [Activity 1]
* [Activity 2]
* [Activity 3]
* [Activity 4]

## 6. Concrete outcomes

Use the exact outcome language from the selected package in `../Packages/strategic_ux_packages.md` and the matching detailed package file.

Format this section as a short list of deliverables that states:

* What the artifact is
* What it contains
* What decision or next step it supports

Example structure:

* [Outcome 1]
* [Outcome 2]
* [Outcome 3]
* [Outcome 4]

## 7. Timeline and working model

Describe how the work will run in practical terms.

Suggested points to cover:

* Total duration
* Activity sequence and dependencies
* Main workshops, interview blocks, or synthesis steps between client activities
* Review and validation points after each activity
* Expected response times from the client
* What pauses the work if input or sign-off is delayed

Suggested structure:

The work will run over `[timeframe]` as a staged sequence of dependent activities. During this period we will complete `[main work blocks]`, with structured synthesis between the main client activities and a review and validation checkpoint after each activity output. The next activity will start only when `[client role]` has reviewed and confirmed `[output]`. To keep momentum, we will need feedback within `[time window]` after each review.

## 8. Client involvement

Be explicit about the client effort required.

Suggested points to cover:

* Who needs to participate
* How much time they need to set aside
* What access or material they must provide
* Who is responsible for validating outputs at each checkpoint

Suggested structure:

We expect approximately `[time commitment]` of client involvement. This includes `[workshops, interviews, reviews, approvals]`. We will also need access to `[users, data, internal experts, existing material]`. `[Client role]` will review and validate the agreed outputs at each checkpoint so the next activity can begin on a confirmed basis.

## 9. Assumptions and dependencies

List the conditions required for the work to succeed.

Examples:

* Access to relevant stakeholders within the first week
* Access to the right users or customer-facing teams
* Access to existing analytics, feedback, or operational material
* Timely review and sign-off at agreed checkpoints
* A named client owner who can confirm when each activity output is accepted
* Agreement that later activities pause if required input or validation is delayed
* Agreement that unknown constraints will be surfaced and confirmed early rather than assumed away

## 10. What this phase will not cover

Make the boundaries clear so the proposal does not overpromise.

Examples:

* Detailed UI design for all screens
* Full technical specification
* Delivery planning beyond the agreed scope
* Implementation of the recommended concept

## 11. Success measures

State how the client should judge whether the discovery phase created value.

Where possible, state each success measure as:

* Baseline today
* Target improvement
* Measurement window after the work is used in delivery

Examples:

* Faster decision-making on scope and priorities
* Fewer major changes once delivery starts
* Clearer view of user needs and service dependencies
* Better basis for investment and sequencing

## 12. Commercials

State the pricing model and what it includes.

Suggested structure:

The investment for this phase is `[amount]`. This includes `[included items]`. It does not include `[excluded items]`, which can be scoped separately if needed.

## 13. Recommendation and next step

End with a direct recommendation.

Suggested structure:

We recommend starting with **[Package name]** so `[Client name]` can make a better decision on `[decision]` before moving into broader delivery. If approved, we can confirm the final scope, the stage-gate review points, and the start date in a short kickoff session.
