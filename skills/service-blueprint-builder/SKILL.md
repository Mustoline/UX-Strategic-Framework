# Service Blueprint Builder

Use this skill for Package C Activity `2.2`: the current-state service blueprint that makes the service model visible across front-stage and back-stage interactions, supporting processes, and dependencies.

This skill should help the team turn fieldwork, ecosystem mapping, and supporting service evidence into a current-state blueprint that shows where the service creates friction, delay, duplication, cost, or lost value and what later target-state work needs to respond to.

This skill should build on the helper layer:

* Use [map-structure-generator](../map-structure-generator/SKILL.md) to create the service-blueprint scaffold, labels, and dependency structure
* Use [artifact-writer](../artifact-writer/SKILL.md) to draft the blueprint readout and summary cleanly
* Use [ux-strategy-reviewer](../ux-strategy-reviewer/SKILL.md) as the final quality check on client-facing outputs
* Use [evidence-ingest](../evidence-ingest/SKILL.md) if additional service, support, or operational evidence needs to be normalized into the current-state view

It should use earlier Package C outputs where relevant:

* [executive-and-service-owner-interviewer](../executive-and-service-owner-interviewer/SKILL.md) for the strategic pressures, risks, and investment questions
* [ecosystem-workshop-facilitator](../ecosystem-workshop-facilitator/SKILL.md) for the agreed service scope, ecosystem boundary, and critical service moments
* [contextual-fieldwork-runner](../contextual-fieldwork-runner/SKILL.md) for the fieldwork summaries, workarounds, hidden effort, delays, and ownership gaps

## What this skill should produce

For most requests, produce a current-state blueprint pack with:

* A blueprint objective tied to the service problem and the decisions ahead
* A current-state service blueprint scaffold and populated synthesis view
* A clear view of front-stage and back-stage interactions, supporting processes, and dependencies
* A summary of delay points, duplication patterns, cost or effort hotspots, and ownership gaps
* A concise readout of what the later target-state service work must respond to

## Operating modes

### Prep

Before building the blueprint, confirm:

* Which service, journey, or operational slice is in scope
* Which fieldwork outputs and ecosystem artifacts are available
* Which teams, actors, systems, channels, and service moments must appear in the blueprint
* Which business or investment questions the blueprint needs to support
* Whether the blueprint will be synthesized from existing notes or built through a live working session

Then:

* Use `map-structure-generator` to prepare the current-state service-blueprint scaffold
* Use the blueprint flow in [service-blueprint-patterns.md](references/service-blueprint-patterns.md)
* Prepare the output structure in [service-blueprint-templates.md](references/service-blueprint-templates.md)

### Run

During blueprinting:

* Keep the blueprint tied to the agreed service scope and critical service moments
* Show how work moves across front-stage, back-stage, systems, and supporting processes
* Make delays, duplication, cost, hidden effort, and ownership gaps visible rather than implied
* Distinguish repeated evidence-backed patterns from isolated incidents
* Preserve where lived reality differs from formal process descriptions
* Pull out the parts of the current model that later target-state work needs to address first

### Synthesize

After blueprinting:

* Produce a current-state service blueprint or structured equivalent
* Highlight the main delay points, duplication patterns, cost or effort hotspots, and ownership gaps
* Distill what the future-state service model must improve
* Show where the current service model is leaking value or creating avoidable risk
* If needed, hand the draft to `artifact-writer` and then to `ux-strategy-reviewer`

## Core blueprint objectives

The current-state service blueprint should answer:

* How does the service work today across front-stage and back-stage interactions?
* Where do delays, duplication, hidden effort, or ownership gaps appear?
* Which systems, processes, or dependencies create the most friction?
* Where is value lost or effort added in the current model?
* What should the later target-state service model change first?

Adapt the output to the service and decision in scope rather than filling every section mechanically.

## Blueprint rules

* Keep the blueprint focused on the agreed service boundary
* Show the relationship between visible experience and hidden supporting work
* Use evidence-backed patterns rather than idealized process logic
* Make ownership and dependency gaps explicit where they matter to service performance
* If the evidence is incomplete, mark that clearly rather than implying a complete model
* Prefer a decision-useful blueprint over an exhaustive documentation exercise

## Minimum output standard

Unless the user asks for something else, return these sections:

1. Blueprint objective
2. Current-state service blueprint
3. Delay and duplication patterns
4. Cost or effort hotspots
5. Ownership gaps and dependency issues
6. What the future-state work should respond to

## Boundaries

This skill covers Activity `C2.2` only. It builds the current-state service blueprint for Package C. It does not replace the later target-state service model, validation, or roadmap work.
