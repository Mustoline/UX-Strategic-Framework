# Future-State Service Model And Validation

Use this skill for Package C Activity `3.1`: the target-state service-model work that turns the current-state blueprint into a future-state direction and tests whether it holds up with the people who need to live with it.

This skill should help the team define how the future service should work across channels, teams, and systems, build a target-state service model that responds to the current-state breakdowns, and validate that direction with relevant users, customers, or internal stakeholders before the roadmap and business-case step begins.

This skill should build on the helper layer:

* Use [workshop-design-kit](../workshop-design-kit/SKILL.md) for agenda, facilitation structure, and playback logic
* Use [map-structure-generator](../map-structure-generator/SKILL.md) to shape the target-state service-model scaffold and validation capture structure
* Use [artifact-writer](../artifact-writer/SKILL.md) to draft the target-state readout, validation synthesis, and refinement log cleanly
* Use [ux-strategy-reviewer](../ux-strategy-reviewer/SKILL.md) as the final quality check on client-facing outputs

It should also build on the existing interview skill where useful:

* Use [discovery-interview](../discovery-interview/SKILL.md) as a source of reusable validation-interview structure, but keep this skill focused on service-model testing and feasibility rather than product specification discovery

It should use earlier Package C outputs where relevant:

* [executive-and-service-owner-interviewer](../executive-and-service-owner-interviewer/SKILL.md) for the strategic priorities, risks, and investment questions
* [ecosystem-workshop-facilitator](../ecosystem-workshop-facilitator/SKILL.md) for the agreed service scope and ecosystem dependencies
* [contextual-fieldwork-runner](../contextual-fieldwork-runner/SKILL.md) for the workarounds, hidden effort, and service-reality patterns
* [service-blueprint-builder](../service-blueprint-builder/SKILL.md) for the current-state blueprint, hotspots, and the issues the future-state model must change

## What this skill should produce

For most requests, produce a target-state service-model pack with:

* A target-state objective tied to the service problem and the decisions ahead
* A timed agenda for a half-day future-state service model workshop
* A target-state service model or structured equivalent
* A validation guide for 5-8 users, customers, or internal stakeholders
* A feedback synthesis showing where the concept held up, where friction remained, and what feasibility signals emerged
* A refinement log showing what changed in the model and what still needs attention

## Operating modes

### Prep

Before the target-state and validation work, confirm:

* Which service, journey, or operating-model slice is in scope
* Which current-state blueprint findings and hotspots matter most
* Which user, customer, or stakeholder groups should take part in validation
* Which feasibility constraints, dependencies, or non-negotiables are already known
* Which decisions the validated model must make easier in the later roadmap and business-case step

Then:

* Use `workshop-design-kit` to shape the half-day future-state service-model session
* Use `map-structure-generator` to prepare the target-state service-model scaffold
* Use the flow in [future-state-service-model-patterns.md](references/future-state-service-model-patterns.md)
* Prepare the output structure in [future-state-service-model-templates.md](references/future-state-service-model-templates.md)

### Run

During the target-state workshop and validation work:

* Keep the model tied to the agreed service scope and the most important current-state hotspots
* Define how the future service should work across channels, teams, systems, and ownership boundaries
* Distinguish the target-state model from detailed implementation design
* Use validation to test whether the direction is credible, understandable, and workable for the people involved
* Capture both positive signals and remaining friction, feasibility concerns, or open questions
* End with a clear view of what the model now implies for the final roadmap and business-case step

### Synthesize

After the workshop and validation:

* Produce a concise target-state service model or structured equivalent
* Summarize the validation feedback across users, customers, or internal stakeholders
* Capture what changed in response to feedback and what remains unresolved
* Distill the main feasibility signals, dependencies, and design pressures for the next phase
* If needed, hand the draft to `artifact-writer` and then to `ux-strategy-reviewer`

## Core objectives

The target-state service-model and validation work should answer:

* How should the service work in the future state across channels, teams, and systems?
* Which current-state breakdowns does the future-state model address first?
* Does the proposed direction hold up when relevant users, customers, or internal stakeholders review it?
* Which feasibility signals, dependencies, or risks still matter?
* What should the later roadmap and business-case work now sequence and justify?

## Facilitation rules

* Treat the target-state session as a service-model decision exercise, not a general ideation workshop
* Keep the model anchored in current-state evidence and service realities
* Validate with the people who can expose real friction, adoption risk, or feasibility issues
* Preserve tension between desirability and feasibility instead of hiding it
* Make changes to the model explicit when feedback leads to refinement
* Prefer a tested, decision-useful model over a polished but unchallenged concept

## Minimum output standard

Unless the user asks for something else, return these sections:

1. Target-state objective
2. Suggested half-day workshop agenda
3. Target-state service model
4. Validation guide
5. Feedback synthesis and feasibility signals
6. Refinements, open questions, and next-step implications

## Boundaries

This skill covers Activity `C3.1` only. It defines and validates the future-state service model for Package C. It does not replace the later roadmap, change-implication, or business-case framing work.
